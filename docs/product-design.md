# GeoScore 产品设计

## 产品定位

GeoScore 是面向国内各行业品牌的 AI 推荐增长工作台。品牌方自行注册、录入品牌资料并发起扫描，系统保存 AI 原始回答与引用，定位品牌在哪些高意图问题上缺席、落后于竞品或缺少官方证据，再把问题级抢位机会转成可执行的增长实验。用户发布实际行动后，手动发起同配置复扫，通过基线与复扫报告验证提及、推荐、引用和 GeoScore 是否改善。

GeoScore V1 提供的是“扫描定位 → 抢位行动 → 手动同配置复测 → 留存证据”的闭环，不承诺无人值守的自动监测或自动增长结果。

## 核心用户旅程

1. 用户通过邮箱密码或中国大陆手机号注册并登录；系统自动建立 FREE 订阅并发放 30 次回答额度。
2. 用户创建品牌，录入官网、行业、核心产品、目标用户、别名与竞品；系统生成发现、痛点、对比和购买决策四类共 20 个问题。
3. 用户选择当前可用的 AI 数据源和 1 至 3 次重复采样。真实数据源与模拟数据源不能混在同一次扫描中，预计消耗为“启用问题数 × 数据源数 × 重复次数”。
4. 用户手动发起扫描，系统原子扣减额度，保存固定问题版本、数据源、重复次数、原始回答、提及、引用和评分快照；执行失败时退还本次额度。
5. 报告展示 GeoScore、五项分数、置信度、风险、建议、逐条原始证据，以及本次扫描产生的问题级抢位机会。
6. 用户从抢位机会创建增长实验，编辑不少于 10 个字符的行动计划和可选目标 URL，再点击“发布行动实验”。
7. 用户完成站外内容或页面动作后，主动点击“开始验证”。模拟数据实验可立即验证；真实数据实验需等到页面标注的最早复查时间后才能手动发起。
8. 验证复扫固定复用基线的问题版本、数据源和重复次数，并要求相同评分算法版本。完成后保存基线与复扫报告链接、指标差值和结论。
9. 额度不足时，用户在套餐页自助购买；支付履约以幂等事务更新订单、订阅、额度账户和额度流水，然后继续手动复扫。

## 真实数据与模拟数据边界

| 维度 | 真实 AI 数据 | 模拟演示数据 |
| --- | --- | --- |
| 数据来源 | 仅来自已实现适配器且凭据有效的平台；当前 V1 的真实适配器为 DeepSeek | 来自本地 `mock` 适配器 |
| 用途 | 品牌业务判断、报告证据和后续人工复查 | 本地开发、自动化测试和完整产品体验演示 |
| 页面标识 | 始终显示“真实 AI 数据” | 始终显示“模拟演示数据”和“仅用于体验闭环，不代表真实 AI 表现” |
| 趋势与报告 | 只与真实数据扫描比较 | 与真实数据分组展示，不得混入真实趋势或对外结论 |
| 实验复查 | 发布或实质修改行动后等待 7 天，再由用户手动发起 | 用户发布行动后可立即手动发起 |
| 对外口径 | 可以引用已保存的原始回答，但必须同时说明平台、模型、时间、样本与置信度 | 不得冒充目标平台回答，不得作为品牌真实表现或商业效果证明 |

未配置 `DEEPSEEK_API_KEY` 时，DeepSeek 必须显示为不可用；没有正式接口或合规采集方式的平台不得伪装成真实接入。模拟数据虽真实写入 PostgreSQL 并走完整业务事务，但其内容仍只是可重复的测试数据。

## GeoScore 与正式评分门槛

```text
GeoScore = 提及度 × 30% + 推荐度 × 25% + 竞品声量 × 20% + 引用度 × 15% + 情感度 × 10%
```

正式评分至少需要 120 条有效回答并覆盖 3 个真实平台。标准配置可由 20 个非品牌问题、3 个真实平台、每个平台重复 2 次组成。样本少于 120 条或平台少于 3 个时必须显示“初步评分”和置信度。

当前 V1 只有一个真实平台适配器，单独使用 DeepSeek 无法达到 3 个真实平台的正式评分门槛，因此必须如实展示初步评分。实验结果表示固定配置下前后指标的变化，不能宣传为严格因果关系或保证排名。

## 抢位机会与增长实验

抢位机会以“问题 × 平台”为最小单位，包含四类：

- `MENTION_GAP`：目标品牌未被提及。
- `COMPETITOR_ADVANTAGE`：竞品出现且目标品牌缺席，或品牌推荐位置落后。
- `CITATION_GAP`：品牌被提及，但缺少可信官方引用。
- `BRAND_RISK`：回答中出现需要品牌方核查的高风险描述。

增长实验状态与用户可见含义如下：

| 状态 | 页面文案 | 含义 |
| --- | --- | --- |
| `DRAFT` | 行动草案 | 已从机会创建实验，尚未发布行动 |
| `ACTIVE` | 行动执行中 | 已保存行动版本，等待用户执行站外动作并手动发起验证 |
| `VERIFYING` | 正在验证 | 用户已发起同配置复扫；中断后可由用户安全恢复 |
| `VERIFIED` | 已验证提升 | 复扫达到当前判定规则，保存“验证有效”和指标差值 |
| `INCONCLUSIVE` | 结果待观察 | 复扫未形成可验证提升，如实保存结果和差值 |

同一实验更新行动计划或目标 URL 会产生新的行动版本；真实数据实验的 7 天观察窗口从实质修改时重新计算。系统不会在到期后自动启动复扫，仍需用户点击“开始验证”。

## 套餐与付费价值

回答额度用于真实控制 AI 调用成本，外部价值表达以品牌数量、问题级抢位机会、增长实验、扫描历史与验证证据为主。月度回答额度分别为 30、500、2500、10000 次，品牌上限分别为 1、1、3、10 个，价格必须保持以下可支付金额：

| 代码 | 套餐 | 月付价格 | 品牌上限 | 回答额度 | 已实现的核心价值 |
| --- | --- | ---: | ---: | ---: | --- |
| `FREE` | 免费体检 | ¥0 | 1 | 30 | 初步可见度报告、问题级抢位机会 |
| `STARTER` | 基础版 | ¥99 | 1 | 500 | 问题级抢位机会、增长实验与手动同配置复测 |
| `PRO` | 专业版 | ¥299 | 3 | 2500 | 扫描历史与趋势对比、引用分析与实验归因 |
| `BUSINESS` | 商业版 | ¥899 | 10 | 10000 | 多品牌增长工作台、跨品牌机会队列与实验归因 |

本地使用 Mock 支付完成下单、支付、订阅和额度发放闭环；生产环境使用 PAYJS 微信扫码支付，并要求商户凭据、回调地址与经营场景审核全部有效。套餐购买不会替用户自动安排扫描，也不会自动发布或验证实验。

## V1 范围

- 中文官网、套餐页、隐私政策和服务协议。
- 邮箱密码注册登录、手机号验证码注册登录、退出和会话保护。
- 品牌、别名、竞品、20 个默认问题及问题版本管理。
- 可用数据源查询、真实/模拟标签、1 至 3 次重复采样和额度预估。
- 原始回答、提及、竞品、引用、评分快照、风险、建议和问题级抢位机会。
- 增长实验创建、行动发布、用户手动同配置复扫、结果归因和中断恢复。
- 免费、基础、专业、商业四档套餐、订单、支付、订阅与额度流水。
- Vitest 单元/集成测试与 Playwright 桌面端、移动端全链路测试。

## 当前明确不包含

- 自动调度、定时扫描或无人值守持续监测。
- 行动发布后的自动复测；真实和模拟实验都必须由用户手动发起验证。
- 团队账号、成员邀请、角色权限或多人协作。
- 报告文件导出、定时邮件或第三方报表投递。
- 自动向第三方媒体发稿，或无人工审批的 CMS 自动发布。
- 未获合规接口的消费端 AI 平台采集。
- 同行业有效品牌少于 30 个时的行业百分位，以及任何“保证排名”承诺。
- 服务器部署、域名备案、第三方商户审核和真实外部凭据验收。

页面、套餐和销售文案不得把以上能力写成已上线功能。

## 完整本地模拟演示

### 1. 环境准备

在 `.env` 中至少配置有效的本地 `DATABASE_URL`，并使用以下演示开关：

```dotenv
BETTER_AUTH_URL="http://localhost:18200"
NEXT_PUBLIC_APP_URL="http://localhost:18200"
AI_PROVIDER="mock"
SMS_PROVIDER="mock"
SMS_TEST_CODE="888888"
PAYMENT_PROVIDER="mock"
```

应用数据库迁移、种子并启动站点：

```bash
npm install
npm run db:generate
npm run db:deploy
npm run db:seed
npm run dev -- -p 18200
```

访问 `http://localhost:18200`。如果 18200 端口已有服务，应先确认该进程同样使用上述 Mock 配置，避免本地演示误调用真实接口。

### 2. 页面闭环

1. 使用唯一邮箱注册，确认控制台显示 FREE 套餐和 30 次额度；手机号本地演示验证码为 `888888`。
2. 创建品牌并确认生成 20 个问题；可编辑其中一个问题以验证问题版本保留。
3. 在品牌页选择“模拟 AI”、重复 1 次，确认显示“模拟演示数据”和免责声明。20 个启用问题预计消耗 20 次，点击“开始扫描”。
4. 打开基线报告，确认显示“初步评分”、逐条证据、本次抢位机会及模拟免责声明；此时剩余额度应为 10。
5. 从一条机会创建增长实验，填写不少于 10 个字符的行动计划和目标 URL，点击“发布行动实验”，确认状态从“行动草案”变为“行动执行中”。
6. 第一次点击“开始验证”，确认接口返回额度不足、页面保留原实验并出现套餐入口；此时不得创建复扫或扣除额度。
7. 从原实验的套餐入口选择 ¥99 基础版并完成本地模拟支付；确认订单已支付、套餐变为基础版，额度增加 500 后为 510。
8. 返回同一个实验页面，再由用户手动点击“开始验证”。模拟实验进入同配置复扫，完成后状态为“已验证提升”或“结果待观察”，并展示 GeoScore、提及率、推荐率、引用率差值。
9. 分别打开基线报告和复扫报告，确认问题版本、模拟数据源和重复次数一致，且两个报告都带模拟标签；第二次扫描消耗 20 次后，额度应为 490。
10. 在品牌页确认真实与模拟趋势分组、开放机会和实验状态均来自已落库数据。

### 3. 自动化验收

```bash
npm test
npm run typecheck
npm run lint
npm run build
PLAYWRIGHT_PORT=18202 npm run test:e2e -- e2e/full-journey.spec.ts
```

完整旅程需要在 Playwright 的桌面端与移动端项目中通过。测试使用独立的 `18202` 端口启动显式 Mock 服务，不复用正在 `18200` 运行的本地预览；整个模拟用例不得请求真实 DeepSeek、PAYJS 或短信服务。
